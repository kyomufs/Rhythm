# tulgusch: M3 Expressive + поведение обновления и кэша — дизайн

**Дата:** 2026-11-03
**Статус:** на ревью оператора
**Класс:** architectural (сквозные слои: тема/моушен, кэш, обновление данных, демо)

**Источник требований:** запрос оператора от 2026-11-03 (15 пунктов) + три уточнённых развилки:
логотип — только глиф-щит монохромом; демо-режим — реальные структуры ТулГУ с явно выдуманной
группой; обновление — единый путь probe → refresh → уведомление для расписания и оценок.

---

## 1. Цель и критерий успеха

Привести tulgusch к Material 3 Expressive (не «M4» — эволюция M3) и заодно закрыть 14 пунктов
поведения и вёрстки.

Успех =

1. Каждая интерактивная анимация в приложении разрешается в одну из шести spring-токенов
   M3E (`{fast,default,slow} × {spatial,effects}`), а не в рукописный `Duration` + `Curves`.
2. Обновление данных имеет один задокументированный путь, одинаковый для расписания и оценок.
3. Расписание и избранное переживают перезапуск приложения без сети.
4. Нативные экраны запуска Android и iOS показывают один и тот же логотип на одном фоне.
5. `flutter analyze` без новых замечаний, `flutter test` зелёный, `flutter run -d linux`
   запускается и проверен визуально.

## 2. Границы

**Входит:** 15 пунктов запроса, тема/моушен/типографика/формы, слои кэша и обновления, демо-данные.

**Не входит:** новые продуктовые фичи, новые зависимости без отдельного согласования, изменение
CI-воркфлоу, `sopka`/секреты, релизные теги, push в GitHub (оператор запретил).

**Осознанно отложено:** `flutter_launcher_icons` / `flutter_native_splash` — обе требуют новых
dev-зависимостей; тот же результат достигается правкой существующих ресурсов (см. §6.3).

## 3. Ключевые решения

| № | Решение | Почему так |
|---|---|---|
| D1 | Схема моушена — **expressive** для всего продукта, `standard` только как fallback при `MediaQuery.disableAnimations` | M3E рекомендует expressive для большинства продуктов; приложение не утилитарное |
| D2 | Spring-токены живут в **одном** файле `lib/core/theme/motion.dart` как `SpringDescription` из `flutter/physics` | Третья сторона не нужна: `SpringDescription.withDampingRatio` и есть spring. Один источник правды для всех потребителей |
| D3 | Кастомные анимации (не компоненты Flutter) едут на `AnimationController.unbounded` + `SpringSimulation` | Ограниченный контроллер срезает overshoot — то есть убивает весь смысл spring |
| D4 | `Color`/`opacity` — только effects-spring (damping 1.0), `position/size/rotation/corner` — только spatial | Самая частая ошибка M3E: «прыгающее» затухание читается как глюк |
| D5 | Кэш расписания уже есть в Hive (`schedule_cache_<value>`), но TTL 24 ч. Меняем на **stale-while-revalidate без жёсткого TTL** для своей группы | Оператор: «моё расписание и избранное должны кэшироваться». Пустой экран при протухшем кэше — хуже, чем устаревшее расписание |
| D6 | Избранное уже персистентно (`favorite_groups` в Hive). Добавляем **кэш расписаний избранных групп** в тот же механизм | Сейчас открытие избранной группы требует сети даже когда она открывалась вчера |
| D7 | Обновление = `ApiAvailability.probe()` → `refresh()` → уведомление **только при успехе** | Дословно требование п.1. При недоступности API «ничего не происходит» |
| D8 | Демо-режим остаётся офлайновым, но наполняется **реальными структурами ТулГУ** (предметы, типы, корпуса, пары, подгруппы, номера групп) и не содержит шуток | П.14 «демо должен показывать только реальные данные и функционал»; вариант «грузить чужую группу через API» отклонён оператором — демо обязано работать без сети |

## 4. Дизайн-система: M3 → M3 Expressive

Единственный сквозной рефактор (п.15). Всё остальное в этой спеке на него опирается.

### 4.1 Источник значений

Числа берутся **только** из `references/tokens.md` и `references/component-tokens.md` скилла
`m3-expressive`. Ни одно значение здесь не выдумано; где величины нет в M3 — помечено явно.

### 4.2 Spring-матрица — точные токены

`md.sys.motion.spring.{speed}.{spatial|effects}.{damping|stiffness}`, схема применяется на уровне
продукта и **не входит в имя токена**.

| Токен | Damping | Stiffness |
|---|---|---|
| `fast.spatial` | 0.6 | 800 |
| `default.spatial` | 0.8 | 380 |
| `slow.spatial` | 0.8 | 200 |
| `fast.effects` | 1.0 | 3800 |
| `default.effects` | 1.0 | 1600 |
| `slow.effects` | 1.0 | 800 |

Standard-схема (для reduce-motion fallback): `0.9/1400`, `0.9/700`, `0.9/300` — effects идентичны
expressive по определению.

**Выбор скорости:** меньше элемент → быстрее. `fast` — чипы, кнопки, переключатели.
`default` — шторки, карточки, частичный экран. `slow` — полный экран.

### 4.3 Шкала радиусов — 10 шагов

`0 / 4 / 8 / 12 / 16 / 20 / 28 / 32 / 48 / full`. Жирным — добавленное в M3E:
**20** (`CornerLargeIncreased`), **32** (`CornerExtraLargeIncreased`), **48** (`CornerExtraExtraLarge`).

**Вложенные радиусы:** `inner = outer − padding`. Никогда не переиспользовать радиус родителя —
это ровно баг из п.7 (см. §4.6).

### 4.4 Типографика — emphasized-стили

Baseline и emphasized живут **вместе**; emphasized не заменяет шкалу, а размечает исключение:
размер и line height совпадают, отличаются вес и tracking.

| Стиль | Размер | Line height | Tracking | Вес |
|---|---|---|---|---|
| `titleSmall` emph. | 14 | 20 | 0.1 | **Bold** |
| `titleMedium` emph. | 16 | 24 | 0.15 | **Bold** |
| `labelLarge` emph. | 14 | 20 | 0.1 | **Bold** |
| `labelMedium` emph. | 12 | 16 | 0.5 | **Bold** |
| `headlineSmall` emph. | 24 | 32 | 0 | Medium |
| `bodyMedium` emph. | 14 | 20 | 0.25 | Medium |

**Флаттер не даёт emphasized-стилей** — это не библиотечная фича. Собираем `TextTheme` вручную из
этих значений (`emphasizedTitleSmall()` и т. п.) в `lib/core/theme/typography.dart`.

**Где применяем:** выделенные пункты навигации, заголовки дней/блоков, номер группы в шапке,
заголовок расширенной карточки, выбранные пункты списков, primary-кнопки. **Не применяем** к
body-тексту и к подписям-подсказкам.

### 4.5 Цвет и регионы

Регион-роли постоянны на всех брейкпоинтах:

| Регион | Роль |
|---|---|
| Тело | `surface` |
| Навигация | `surface container` |
| Текст | `on surface` / `on surface variant` |
| Разделители внутри компонентов | `outline variant` |
| Граница таргета (обводка карточки-цели) | `outline` |

Активные пункты навигации: в flexible nav bar **active label = `secondary`** (изменение M3E; в
baseline было `on surface variant`). Иконка — контейнеры как заливка, поверх — только `on *` роли.

### 4.6 П.7 — согласование радиусов в блоке дня

**From M3:** `inner = outer − padding`; радиусы берутся из 10-шаговой шкалы.
**My design decision (не в M3):** наружный радиус блока дня — 20 (`CornerLargeIncreased`),
внутренний отступ карточки пары — 4, значит внутренний радиус 16 (`CornerLarge`).

Сейчас `DaySchedule` рисует внешний радиус 20 с `Clip.antiAlias`, а `LessonTile` внутри при
`isOngoing` рисует **собственную** обводку радиусом 12 — на первом и последнем предмете дня она
не совпадает с дугой родителя и торчит за неё. Лечение: обводку «идёт сейчас» поднимаем на уровень
дня (родитель знает индексы), плитка получает флаг и рисует только заливку без собственной границы.
Плюс явный `padding` карточки, чтобы `inner = outer − padding` выполнялось численно.

## 5. Поведенческие слои (пп. 1, 2, 10, 11, 14)

### 5.1 Слой доступности API и обновление (п.1, п.10)

Новый сервис `lib/core/services/update_coordinator.dart`:

```
enum UpdateOutcome { updated, unavailable, failed }

class UpdateCoordinator {
  Future<UpdateOutcome> refreshSchedule();
  Future<UpdateOutcome> refreshMarks();
}
```

Порядок строго как в требовании:

1. `ConnectivityService.checkConnectivity()` — probe (сейчас это GET `/GetDictionaries.php?term=`).
2. **Недоступно** → `UpdateOutcome.unavailable`, состояние не меняется, **никакого сообщения**.
   Кэш остаётся на экране.
3. **Доступно** → выполняется обновление.
4. **Успех** → `UpdateOutcome.updated` + `SnackBar` внутри приложения.
5. **Провал при доступном API** (5xx, таймаут) → `UpdateOutcome.failed` + сообщение с причиной.

Потребители: `ScheduleScreenNotifier.refresh()` и `PerformanceNotifier.loadMarks()` переводятся на
координатор. `RefreshIndicator` (п.10) перед обновлением показывает `AlertDialog` подтверждения
`Обновить расписание?` / `Отмена` / `Обновить`; при отмене — ничего.

**Отменённое поведение:** pull-to-refresh при офлайне больше не пишет «Нет подключения к
интернету» — он молчит (это и есть «ничего не происходит»).

### 5.2 Кэш (п.2)

`CachedSchedule.isValid` (24 ч) перестаёт быть гейтом для показа: `getCachedSchedule` отдаёт
снимок любого возраста, а поле `cachedAt` уходит в состояние как `dataAge`. Жёсткий TTL остаётся
только в `clearOldCache()` (7 дней) как защита от разрастания Hive.

Избранное: `getFavoriteGroups()` уже персистентно. Добавляется предзагрузка —
`prefetchFavorites()` проходит по списку и раскладывает снимки в те же ключи
`schedule_cache_<group>`, поэтому открытие избранной группы офлайн работает.

**Проверка:** тест «кэш старше 24 ч всё равно показывается» + тест «избранная группа открывается
офлайн из снимка».

### 5.3 П.11 — баг «только моя группа» в расширенном меню

**Наблюдение:** в `_GroupBadgeBar` чипы избранного строятся из `state.favoriteGroups`, а
`addFavoriteGroup` пишет в Hive и обновляет состояние из `_storage.getFavoriteGroups()`. Список
читается корректно.

**Гипотеза (требует подтверждения прогоном):** «расширенное меню» — это `SchedulePreviewScreen`,
открытый из чипа избранного. Его заголовок — `widget.title`, всегда `fav.groupNumber`, а сам экран
качает расписание по `widget.searchValue`; для избранной группы значение совпадает с номером,
поэтому выглядит как «показывает только моя группа». Вторая половина бага: в
`LessonDetailSheet` блок «Группы» рендерит `lesson.groups`, а в расписании **своей** группы API
отдаёт одну запись — и список схлопывается в одну строку.

Диагностический шаг перед правкой обязателен: прогнать офлайн-сценарий с группой из избранного и
зафиксировать фактическое наполнение `groups`. **Не верифицировано:** точный сценарий, который
оператор называет «расширенным меню», — уточняется первым шагом реализации, а не догадкой.

### 5.4 П.14 — честный демо-режим

Переписывается `lib/core/demo/demo_schedule.dart` и `demo_marks.dart`:

- предметы, типы занятий, корпуса и аудитории — реальные для ТулГУ;
- сетка пар — реальная (5 пар, те же интервалы), группа явно выдуманная (`221341:00-демо`),
  чтобы демо нельзя было спутать с личным расписанием;
- **удаляется** всё «фантазийное»: шуточные названия, `isDemo`-чипы «ДЕМО», синтетические мутации
  `mutateDemoLesson`, подмена случайной пары при refresh;
- журнал изменений в демо наполняется правдоподобными записями (перенос аудитории, отмена), но
  без пометки «ДЕМО» в UI;
- вкладки заметок и оценок в демо работают на реальном функционале, а не на заглушках.

**Функционал в демо остаётся полным** — все экраны, все жесты. Отличие ровно одно: данные
синтетические и помечены на уровне данных, а не UI.

## 6. Платформенные пункты (пп. 3, 6)

### 6.1 П.3 — одинаковая анимация запуска

**Диагноз (проверен по файлам):**

| Платформа | Сейчас | Что видит пользователь |
|---|---|---|
| iOS | `LaunchScreen.storyboard` + `LaunchImage.png` — **PNG 1×1 пиксель** | белый фон, логотипа нет |
| Android 12+ | системный `SplashScreen` API подставляет adaptive-иконку | иконка приложения |
| Android ≤11 | `drawable-v21/launch_background.xml` = `?android:colorBackground` | пустой фон системного цвета |

Три разных экрана — отсюда «на айфоне нету, на андроидах только на новых».

**Решение:** один источник — существующий `tool/app_icon_glyph.png` (белый глиф, альфа-канал),
наложенный на фирменный градиент `#6750A4 → #3B46CD` из `ic_launcher_background.xml`.

- **Android** — `launch_background.xml` в `drawable/` и `drawable-v21/` получает
  `<item android:drawable="@drawable/ic_launcher_background"/>` + центрированный
  `<bitmap android:src="@drawable/ic_launcher_foreground"/>`. Android 12+ берёт
  `windowSplashScreenBackground` и `windowSplashScreenAnimatedIcon` в `values-v31/styles.xml` из
  тех же ресурсов — иконка та же, значит поведение совпадает.
- **iOS** — `LaunchScreen.storyboard`: фон меняется с белого на фирменный градиент/цвет,
  `LaunchImage` пересобирается в 1×/2×/3× из настоящего логотипа вместо пикселя.

Регенерация — расширение существующего `test/icon_generator_test.dart` (guarded
`TULGUSCH_GEN_ICONS=1`), отдельные пакеты не нужны.

### 6.2 П.6 — логотип и номер группы в шапке

**From M3:** `AppBar` — `LeadingSpace` 4dp, `IconSize` 24dp, `AvatarSize` 32dp.
**My design decision (не в M3):** логотип-щит 28dp монохромом в `onSurfaceVariant` слева от номера
группы; надпись «Расписание» из угла убирается.

Источник — `/home/kyomufs/Downloads/logo.png` (1254×1254, белая плитка с чёрным глифом «ТулГУ
1930»). Обрезаем до голого щита с «Т», убираем белый фон и текст, кладём в `assets/branding/`,
подключаем в `pubspec.yaml`. Инструмент обрезки — `magick` (в PATH).

## 9. Риски

| Риск | Митигация |
|---|---|
| Emphasized-типографика — не библиотечная фича Flutter, возможны расхождения весов | Веса задаются явно в `TextTheme`; проверка визуально на linux |
| `Flutter` не имеет нативной поддержки spring-токенов (в `motion.md` статус «Unavailable») | Реализуем сами через `SpringSimulation` — это и есть предписанный путь «use the spring tokens directly» |
| Смена TTL кэша может показать очень старое расписание | В UI добавляется индикатор возраста данных; ручное «Очистить кэш» остаётся |
| iOS launch screen нельзя проверить на этой машине (NixOS, нет Xcode) | Правка ресурсов + проверка структуры ассетов; **не будет проверено на устройстве** |
| П.11 может оказаться не тем багом, что предполагает гипотеза | Первый шаг реализации — воспроизведение и фиксация фактов до правки |

## 10. Порядок реализации

1. Фундамент темы (spring, shapes, typography) + тесты токенов — без него остальное будет
   расходиться.
2. Слой обновления и кэш (пп. 1, 2, 10) + тесты.
3. Демо-режим (п. 14) + тесты.
4. Воспроизведение и починка п.11.
5. Вёрстка: шапка (6, 9), блоки дня (7), меню недели (8), нижнее меню (4), шторки (5),
   расширенная карточка (12), изменения (13).
6. Нативные splash-ресурсы (3).
7. Прогон analyze + test + запуск на linux.
